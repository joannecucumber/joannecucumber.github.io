囂搞發票：用 IP 合作擴大發票載具用戶

把發票載具與 IP 養成結合，並將第一支 KOL App 做成可替換模組；載具綁定率 74–81%，後續產品上架週期由 3 週縮短至約 1 週。

專案總覽

第一支 IP 合作產品，也要成為後續合作的樣板

CMoney 原本已有發票載具產品。為了擴大載具用戶，這次與 IP 合作，把存發票轉成有角色陪伴與養成回饋的體驗；囂搞發票是這個方向的第一支 KOL 發票 App。

這支 App 不只要讓粉絲願意使用載具，也要驗證後續合作能否快速複製。發票與載具流程維持一致，角色、插畫與配色則整理成可替換的表現層，讓每個新 IP 不必重新設計整套產品。

產品挑戰

一次合作，同時處理使用體驗與產品規模化

IP 合作帶來兩個相連、但衡量方式不同的問題。角色不能只是裝飾，也不能讓存發票的主流程變得更難用；同時，第一支 App 還要建立可延伸的產品基礎，避免每換一個 IP 就重做流程、版面與工程。

USER EXPERIENCE

讓粉絲願意持續存發票

把角色陪伴與養成放進使用循環，但不增加載具綁定、查詢與出示條碼的操作負擔。

PRODUCT SCALE

讓下一次合作不用從頭開始

先建立固定骨架與替換規則，降低每支 KOL 發票 App 的設計與開發成本。

問題重構

不是替既有產品換皮，而是定義一套共享架構

每個 IP 的角色比例、動作與視覺語言都不同；如果畫面每次都跟著角色重新排版，合作越多，維護成本就越高。問題因此被重新拆成兩層：哪些能力屬於發票產品，必須保持穩定；哪些內容代表 IP，可以在不影響主流程的前提下替換。

FIXED

固定的產品骨架

發票查詢、載具條碼、登入與設定等核心流程維持一致，讓使用者與工程都有穩定預期。

VARIABLE

可替換的 IP 表現層

角色、插畫、配色、按鈕與養成素材收進同一組版面區塊，保留每個 IP 的辨識度。

設計目標

兼顧載具使用、IP 體驗與後續複製

  1. 01
    主流程保持清楚

    角色與養成融入產品，但發票查詢、載具條碼與設定仍然容易找到、容易使用。

  2. 02
    IP 特色能被看見

    透過角色陪伴、圖鑑與載具造型，讓粉絲感受到合作內容，而不是只看見換色的發票工具。

  3. 03
    建立可重複使用的做法

    把固定版面、素材尺寸與替換規則交付給圖文作家與工程，支撐後續 KOL 產品線。

整體策略

固定骨架、替換內容，再用輕量回饋串回載具使用

01

固定核心流程

共用發票與載具架構，不因 IP 差異重畫主流程。

02

模組化表現層

預先定義角色、插畫、按鈕、底色與養成階段的替換位置。

03

維持輕量養成

用收集發票推進角色成長，讓回饋服務載具使用，也能沿用到其他 IP。

設計原則

01．把替換邏輯寫成能直接使用的規格

只有版面邊界還不夠，圖文作家與工程需要知道每項素材如何放進產品。角色圖、插畫、按鈕、底色與養成各階段的位置和尺寸被整理成同一份規格；每個 IP 只需替換素材與色票，不必重畫主流程，工程也不必大改。

02．讓 IP 出現在使用循環，而不是蓋過主功能

角色陪伴需要和存發票發生關係，才不會成為與產品分離的裝飾。養成因此只保留收集發票、解鎖階段與更換造型等簡單回饋；發票與載具仍是主流程，IP 角色則出現在養成、圖鑑與載具造型中。

03．讓第一支產品直接驗證後續複製方式

囂搞發票使用的不是一次性版型，而是後續 KOL 發票 App 的共同起點。固定骨架確保主功能一致，可替換區域保留 IP 差異；當新角色的比例與動作不同時，仍能先在既有規則內完成適配。

衡量方式

分開看單一產品表現與產品線效率

不同數據回答不同問題：載具綁定率、商店評分與平台推薦反映囂搞發票本身；上架週期則反映模組在後續產品線的效果。這些結果不被合併成單一成功指標，也不把商店曝光或整體綁定率歸因於某一個設計決策。

囂搞發票獲得 Google Play 2022 年度最具潛力應用，並於 2023 年 1 月登上 App Store 首頁推薦。以這支 App 建立的 IP 模組也延伸成後續 KOL 產品線，上架週期從 3 週縮短到 2 週，再縮短至約 1 週。

最終設計

一套載具骨架，承接角色養成、圖鑑與造型

最終產品把發票、載具、養成與設定放在同一套資訊架構中。使用者可以用收集發票推進角色成長，也能查看圖鑑與更換載具造型；IP 體驗被放進產品循環，但不改變載具工具的基本使用方式。

反思與下一步

可複製不是把所有 IP 做成一樣

第一支合作 App 同時成為後續樣板，關鍵是先定義「什麼固定、什麼可以換」。這讓後續合作不必從頭開始，也讓產品、圖文與工程能使用同一套規則協作。

模組化同時會限制 IP 的表現空間。當角色特色需要新的互動，下一步應先評估差異帶來的使用價值與製作成本，再決定要留在既有規格內，或為產品線擴充新的模組。
